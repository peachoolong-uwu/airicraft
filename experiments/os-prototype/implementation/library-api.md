# Immutable definitions and installations

This implements the local library/lifecycle portion of [issue 63](https://github.com/shinohara-rin/airicraft/issues/63). It uses the existing [execution pool](execution-api.md) and invocation broker. The prototype entrypoint is still separate; this is not yet the mixed-duty execution loop.

## Content and evidence

`DefinitionLibrary.open(directory)` owns a Git-friendly content store. `candidate(definition, proposal)` validates and writes an immutable manifest under `revisions/<sha256>/definition.json`. The digest covers source or prompt, schemas, exact dependency digests, requirements and examples. Display names are discovery metadata, never resolution authority. `list` filters name, tags, required capabilities, top-level input/output type and compatible environment; `get` rechecks content and record hashes. Omitting the environment filter searches all definitions; supplying it requires every declared requirement to match.

A definition declares schema version 1, kind, name/description, tags, capabilities, environment requirements, dependency aliases, input/output contracts and examples. Behaviors additionally declare `source` and mode `generator` or `offers`. Workers declare `prompt`, a named `profile` requirement, and a fallback dependency alias. They can declare `reconsideration: {fingerprint: [field, ...]}` to guard repeated decisions for a named physical failure; this optional rule is part of the immutable revision. Worker fallback input/output schemas must match exactly. Profiles contain no credentials in this library.

Contracts use a deliberately closed JSON Schema subset: booleans; null/boolean/number/integer/string/array/object types; enum; numeric and length bounds; items; named properties; required keys; and boolean additionalProperties. Objects are closed by default. Unsupported keywords, accessors, non-JSON values and coercions are rejected. Schemas are bounded to eight levels and 256 nodes; values retain the execution boundary's 16 KiB, sixteen-level and 2,048-node limits. The broker's result validator checks both terminal generator values and every offer array before they are returned to the host caller. Physical obligations still delay failure completion.

Source/prompt is at most 64 KiB; the complete manifest is at most 512 KiB under the closed-value traversal limit. The local store allows 256 revisions and 128 immutable lifecycle records per revision. Records have a sequence and previous-record digest and use exclusive creation plus file fsync. Installation admission reserves a record slot for each active binding's retirement. Lifecycle records use a 32 KiB, twenty-level, 4,096-node envelope, allowing a full bounded outcome plus release metadata without changing guest limits. Repeating retirement with the identical outcome is idempotent, including after a durable write whose reply was lost; changing that evidence is a conflict. An ambiguously acknowledged installation record is queried before its root is forgotten, and a discovered active binding is retired. Unavailable metadata retains that root for reconciliation. Capacity exhaustion fails visibly; there is no automatic deletion of controls or failed candidates. This is bounded host-owned experiment storage, not a hostile-filesystem isolation boundary or a general package manager.

`resolve` follows the explicit local dependency lock, bounded to 32 definitions and eight levels. Every dependency must already be validated. Cycles include their concrete path; missing revisions, incompatible environment and insufficient grants reject installation. Each parent must declare the capabilities required by its dependencies, allowing child grants to remain within the parent's authority.

`LibraryValidator.validate(digest)` resolves a candidate and replays its examples in the shared `RunnerPool`. Validation therefore consumes the same global root/invocation capacity and root CPU/memory budgets. A temporary controller root owns the example VMs and consumes their distinct outcomes. It has no world-effect dispatcher: emitted effects are compared as data, never executed.

Generator examples contain `input`, `responses`, and `expected` step results, with one more expected step than responses. Offers examples have one expected offer array per response/view. At least one example is required to validate; an example may stop at a yield when its purpose is that bounded prefix. Input/output contracts are checked independently of expected values. Worker examples contain input and example result; validation checks these schemas and the validated fallback contract. This does not call a model or qualify inference. Evidence always states deterministic scope, `liveQualified: false`, and `inferenceQualified: false`; relevant fixture evidence remains a later gate. Failed validation retires the candidate while retaining its source and evidence.

`recordValidation`, `recordInstall` and `recordRetired` are trusted host evidence APIs. A manually supplied passed record is not a substitute for the validator or required fixture qualification. Installation and release authority comes from `InstallationHost` and `InvocationBroker`, not from guest-authored metadata. A partial/corrupt lifecycle file fails closed; repair after a storage failure is not an automatic replay path.

## Installation and replacement

Construct `InstallationHost` with the library, existing invocation broker/pool, authorized grants, environment identity, run ID, trace and a read-only `refresh(input)` callback. The callback must obtain fresh bounded world evidence through the native observation service; it has a two-second installation deadline. This initial snapshot is context, not action authority. Each later physical admission still uses its own checked native frame.

- `install(digest, {input, grants?})` validates inputs, pins the complete closure, initializes a fresh VM, records the installation, and refreshes observations before exposing it. The record retains the exact input and its separate digest, granted capabilities, closure, environment and execution-policy identity. Only the definition's required subset of the authorized grants is assigned.
- `spawn(parentId, alias, input, {grants?, failurePolicy?})` resolves only the parent's pinned aliases, checks typed inputs and attenuated grants, and creates an owned child VM. Worker dependencies are reserved for the separate worker service. `join` consumes the broker's authoritative child outcome.
- `resume` and `offers` execute the pinned source. A raw generator `done` result is body completion only; use the broker outcome or `advance` retirement result to establish complete success. A returned parent can still have running children and physical obligations.
- `replace(installationId, digest, options?)` checks the candidate before stopping the old root. Default grants are the old root's grants; a revision cannot silently broaden authority. It stops new offers and cancels owned children/subscriptions. `advance()` waits for the old broker outcome before closing its process, recording retirement, and starting a new invocation with a new observation. It re-resolves validation requirements at the new start. It never edits running frames or swaps dependencies underneath them.
- `stop` also discards a pending replacement. `close` stops all owned roots and prevents late asynchronous setup from publishing another installation. Call `advance` after the activity coordinator reconciles physical work; unresolved cleanup remains retained and blocks replacement. Independent roots and other subscribers of a shared service continue normally.

`advance` returns bounded retirement/replacement transitions and consumes terminal root slots. It reports a failed replacement separately after the old root has retired; it does not silently restart the old revision. Rollback is an explicit installation of the retained old digest with current inputs, never a reversal of world effects. The durable native journal still governs host-crash reconciliation. Library metadata does not restore JavaScript frames or authorize replay of prior actions.

The [generator loop](loop-api.md) now dispatches host effects, and the [worker service](worker-api.md) owns inference subscriptions, fallback VMs and a per-run cache. `workerDefinition(id, alias)` supplies the pinned worker/fallback pair and rejects capabilities or a nongenerator fallback. Cache identity includes the immutable revision; replacement cancels old subscribers through ordinary invocation ownership. Context scheduling and full live fixture qualification remain subsequent integration work. No Minecraft efficiency claim follows from these deterministic lifecycle checks.
