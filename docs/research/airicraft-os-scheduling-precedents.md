# Airicraft OS scheduling precedents

Research for [Establish scheduling precedents for asynchronous skills sharing one player](https://github.com/shinohara-rin/airicraft/issues/55), within [Chart the Airicraft OS driver experiment](https://github.com/shinohara-rin/airicraft/issues/51). Sources checked 2026-09-15; repository evidence inspected at `9af5e6ec561d6652a2f788603276f05991c4d893`. Research only: no scheduler, API, language, or framework is selected.

The useful precedents separate **behavior lifetime**, **permission to actuate**, **background world progress**, and **computational work**. They provide contracts for waiting, child ownership, cancellation, and contention. They do not supply a complete scheduler for one embodied player. The applications and candidate constraints below are analysis for later design decisions, distinct from the documented facts in the comparison.

The experiment's fixed scope is external Codex authoring and revising code-defined behaviors from evidence. Airicraft OS executes and orchestrates those behaviors. Callable LLM workers may return judgments, including scheduling judgments; they are not a new embedded author or planner. A separate local sandbox process is permitted, but its runtime and process boundary remain open.

## Existing Airicraft boundary

The current implementation is a narrower precedent, not the proposed OS:

- Graph watches release the single foreground slot when a graph becomes `WATCHING`; passive polling can update facts without dispatching primitives. Fulfilled watches queue by fulfillment tick, then creation order, and do not preempt the current foreground graph. Admission also respects the next runnable slot. This is bounded cooperative scheduling, not a general scheduler for arbitrary code-defined behaviors. [Watch contract](../superpowers/specs/2026-06-16-action-graph-watches.md), [coordinator: `submit`, `pollSuspended`, `resumeRunnable`, `updateForegroundResidency`](../../src/client/java/ai/moeru/airicraft/agent/actions/ActionGraphCoordinator.java).
- Unified work exposes parent IDs, lifecycle states, and foreground status over existing executors. Graph children are controlled through their parent. Furnace tracking is background work; canceling its tracking leaves the physical furnace and items unchanged. The work projection explicitly has no scheduling authority. [Work snapshot](../../src/client/java/ai/moeru/airicraft/agent/work/WorkSnapshot.java), [work tools](../../src/client/java/ai/moeru/airicraft/agent/work/WorkToolProvider.java), [work projection](../../src/client/java/ai/moeru/airicraft/agent/work/WorkProjection.java), [accepted work ADR](../adr/0002-system2-evidence-work-and-decisions.md).
- Reflexes already separate decision activity from actuator ownership, with safety epochs and exact interrupted-work identities guarding handback. The accepted ADR also retains evidence independently of model wakeups and rejects stale responses. Its embedded controller/thinker split describes production today; the experiment's external-author scope deliberately differs from that split. This note does not amend the ADR. [Reflex contract](../architecture/reflex/README.md), [work/evidence ADR](../adr/0002-system2-evidence-work-and-decisions.md).

## Four precedent families

| Precedent | What the primary source actually provides | What Airicraft still has to define |
| --- | --- | --- |
| **Temporal workflows, activities, and messages** | Durable timers suspend workflow execution without occupying the worker process. Activities are ordinary functions, can be nondeterministic, and return recorded results; failed attempts restart unless application checkpoints are used. Idempotency is recommended. A Signal acknowledges server acceptance before workflow processing. Async handlers interleave at awaits; locking and explicitly waiting for all handlers to finish address distinct hazards. [Timers](https://docs.temporal.io/develop/python/workflows/timers), [activities](https://docs.temporal.io/activities), [Python message handling](https://docs.temporal.io/develop/python/workflows/message-passing) | Workflow waiting does not release an application-defined player claim. Recorded activity completion is not proof of current world state. Minecraft effects require their own reconciliation; retrying a harvest, transfer, or feeding operation cannot be treated as retrying a pure function. No adoption of Temporal infrastructure or durable replay is implied. |
| **Trio structured concurrency** | A nursery cannot finish until its children finish, and child failures propagate. Unhandled failures cancel sibling tasks. Cancellation is cooperative at checkpoints; shielding can protect cleanup with a separate timeout. A condition wait explicitly releases its lock and reacquires it before returning. Synchronization primitives serve the longest-waiting task first. [Nursery tutorial](https://trio.readthedocs.io/en/stable/tutorial.html#okay-let-s-see-something-cool-already), [core contracts](https://trio.readthedocs.io/en/stable/reference-core.html) | Structured lifetime does not serialize children's physical actions or release arbitrary resources at every await. Define which scope owns a child, which failures stop siblings, and how independent long-lived behaviors are supervised. Safe cleanup and actor transfer must be implemented by the game-facing layer. Trio is a contract example, not a Python runtime recommendation. |
| **ROS 2 long-running actions** | Goals have identities, acceptance, feedback, and terminal results. Cancellation can be rejected. Accepted cancellation enters `CANCELING`, allowing application cleanup; the cancel response does not certify terminal `CANCELED`. Completion is reported through the result/status mechanisms. Result retention is configurable. [ROS 2 action design](https://design.ros2.org/articles/actions.html) | The protocol does not define a universal physically safe stop, exclusive player ownership, or a scheduler across action servers. Airicraft must define the observable handover condition for navigation, mining, interactions, and reflex takeover, including failure to stop and residual world effects. Cancellation and pause/resume are separate contracts. |
| **Resource models and priority inheritance** | SimPy distinguishes limited reusable resource slots, consumable quantities in Containers, and concrete objects in Stores. Priority queues and preemptive resources are separate options; preemption interrupts the modeled process, whose code handles the interruption. Linux RT-mutexes boost a lock owner to a higher-priority waiter's priority, propagate boosts along lock dependencies, and remove boosts on release. Waiters use priority order and FIFO within equal priority. [SimPy resources](https://simpy.readthedocs.io/en/stable/topical_guides/resources.html), [Linux RT-mutex contract](https://docs.kernel.org/locking/rt-mutex.html) | SimPy models a world; it does not control Minecraft. A mutex does not reserve consumables or prove safe actuation. Priority inheritance addresses a blocking dependency, not general starvation, deadlock, crop speed, or travel efficiency. Airicraft needs an explicit resource model and a definition of useful service before choosing fairness or priority policy. |

## Consequences for the experiment

**An await is not an actor handover.** A coroutine may yield CPU execution while still holding a lock, waiting for its child, or owning an active navigation command. Conversely, a passive crop watch may release actuation while remaining a live behavior. Trio's resource scopes make this distinction explicit: a capacity token remains borrowed across an awaited operation until the scope exits. [Trio capacity limiter](https://trio.readthedocs.io/en/stable/reference-core.html#trio.CapacityLimiter). Airicraft analysis: CPU time slicing changes which code runs; it does not move the player to another worksite, restore the previous selected item, release input, or reconcile an interrupted interaction. Arbitrarily alternating farming and mining code therefore cannot establish safe or useful sharing.

**Passive waits and active children need different ownership rules.** For a proposed farming behavior, waiting for crop maturity should be distinguishable from waiting for a navigation child that is still using the player. A parent holding the sole actor claim while awaiting a child that also requires it creates a dependency cycle. Candidate contracts include explicitly transferring a claim to a child, retaining a parent-owned claim with one authorized child executor, or releasing and reacquiring at defined boundaries; the choice is open. Whichever is chosen must prevent parent and child from issuing competing actions. Structured child lifetime also does not mean all farm, mine, and animal-care behaviors must be siblings in one fail-fast scope.

**Preemption requires an effects boundary.** ROS distinguishes the cancellation request from completed cancellation; Temporal similarly distinguishes graceful cancellation from forceful termination, which gives workflow code no cleanup opportunity. Its Python activity cancellation also depends on heartbeats for delivery to non-immediate activities. [ROS cancellation protocol](https://design.ros2.org/articles/actions.html#cancel-goal-service), [Temporal cancellation](https://docs.temporal.io/develop/python/workflows/cancellation). For Airicraft, a protocol to evaluate is: request interruption, stop or fence old actuation, observe the defined stopped state, record partial effects, then permit handover. This sequence is a candidate review model, not a chosen API. Ordinary preemption, emergency reflex takeover, pausing, and terminal cancellation may need different guarantees. “Resume” must say whether it continues a primitive, restarts from a checkpoint, or recomputes from fresh evidence.

**Resource accounting extends beyond the player.** In the reference workload, the player is reusable exclusive capacity; a furnace or tool is an identified reusable asset; wheat and fuel are consumed; deposited ingredients and future output carry ongoing claims. These are application distinctions suggested by the resource precedents, not existing OS types. A behavior can release the player yet retain a legitimate furnace/output claim. Conversely, reserving all observed wheat for breeding could obstruct food production even while the reserving behavior sleeps. Allocation decisions need rules for identity, quantities, reservation versus actual consumption, external changes, and release on interruption. Acquisition ordering or atomic bundles are candidates for avoiding multi-resource dependency cycles; neither is selected here.

**Fairness needs a unit and eligibility conditions.** FIFO acquisition and priority inheritance are different promises. An urgent food behavior blocked by a lower-priority owner of a needed asset might benefit from expediting the owner's release-producing work. Raising a crop watch's CPU priority cannot make a non-ticking crop grow. Fair dispatch order also does not bound waiting if the current actor owner never reaches a handover point. Questions remain about deadlines, aging, service quotas, dependency donation, and the longest acceptable uninterrupted action. Counting coroutine resumes, wall-clock occupancy, actor-active ticks, completed useful steps, and travel-inclusive service would produce different notions of fairness. These are policy alternatives, not recommendations for the final scheduler.

**World progress is not elapsed wall time.** The existing `AREA_TICKING` watch model checks world/dimension identity, loaded anchor chunk, and client-visible simulation distance before consuming its timeout. It still evaluates completion while progress is paused. That is an explicit eligibility model, not proof that a particular crop or machine advanced. [Progress eligibility contract](../superpowers/specs/2026-06-16-action-graph-watches.md#progress-eligibility). The OS must preserve the distinction between unknown progress, ineligible progress, and observed completion. Farming, smelting, and animal care need individually verified progress conditions. Leaving a site to mine may change both progress eligibility and the cost of returning. A policy comparison should include travel, reacquiring line of sight/reach, equipment or inventory setup, partial-work recovery, and any presence requirement; none of the surveyed generic contracts supplies those Minecraft costs.

**Event receipt, current state, and task outcomes differ.** Temporal's Signal acceptance and ROS's cancel acceptance demonstrate why a receipt cannot stand in for completion. Airicraft already distinguishes evidence incorporation from request dispatch and recorder time, and has bounded histories with explicit gaps. [Work/evidence ADR](../adr/0002-system2-evidence-work-and-decisions.md). Candidate OS event contracts need identities and sequence/cursor semantics, duplicate handling, retention/gap reporting, and a way to inspect the latest authoritative state. Waiting must close the race between checking a condition and subscribing. Define whether an event is an edge, a persistent predicate, or a historical outcome; a fulfilled condition can cease to hold before the behavior reacquires the player. No universal exactly-once physical effect follows from reliable message delivery.

**LLM latency belongs outside actor ownership unless the action requires it.** An LLM judgment can be modeled as identified asynchronous computational work, an analogy also made explicitly for memoized reads in Temporal's activity documentation. [Temporal activities](https://docs.temporal.io/activities). In this experiment, a pending judgment need not prevent unrelated admitted behavior from using the player. Its result should identify its requesting behavior/revision and the snapshot/evidence basis against which it was evaluated. Exact fields remain open. Revalidation is needed when world identity, work generation, resource availability, safety ownership, or action-relevant observations change while the worker runs. A scheduling judgment can rank eligible options; game-facing validation must still check a proposed choice when it is applied. Timeout, supersession, worker failure, call limits, and whether results remain useful after parent cancellation are separate decisions.

## Enforceable constraints and generated policy

The fixed single-player premise implies one authoritative actuation boundary. The precedents motivate keeping that boundary independently enforceable even if code or LLM workers generate scheduling policy. Candidate enforcement responsibilities include validating current ownership/generation before an effect, preventing conflicting resource allocations, recognizing terminal versus stopping work, and rejecting inapplicable observations or responses. Exact mechanisms and permitted exceptions require design decisions.

Policy may decide which eligible behavior is useful, how to trade urgency against travel, what materials to allocate, and when an ordinary interruption is worthwhile. It cannot make an unavailable resource exist or make a stale actor claim current. Hard admissibility constraints must be distinguishable in evidence from estimated costs and preference scores. LLM-proposed schedules therefore need the same validation as code-proposed schedules; immediate reflex response cannot depend on a pending judgment.

A sandbox process may isolate execution faults, but terminating it alone does not establish that an already-issued in-game action stopped. The process boundary needs a defined ownership-loss behavior. Codex-authored revisions also need an installation boundary: stop and replace, drain existing invocations, or version/coexist under explicit rules. This research leaves those alternatives open and does not introduce a runtime author.

## Questions for later tickets

| Decision area | Concrete question the evidence leaves open |
| --- | --- |
| Behavior and child lifetime | What owns each invocation, watch, primitive, LLM call, and background process? Which children must be joined or canceled before the parent can finish or be replaced? |
| Actor ownership and handover | Which waits release the player, which retain an active child, and what evidence permits ordinary or emergency handover? What happens when stopping fails or the sandbox disappears? |
| Material and asset allocation | Which resources require reservations, how are partial consumption and deposited items represented, and who owns output after cancellation? What detects external changes or allocation deadlock? |
| Priority and fairness | Which promises are required: bounded response, starvation prevention, dependency priority donation, useful work share, or something else? How are travel/setup and non-preemptible intervals charged? |
| Progress and observations | Which workload-specific predicates prove progress eligibility and completion? What closes subscription races, reports event gaps, and determines freshness at resumption? |
| Callable judgments | What snapshot and revision accompany a request? How are latency, concurrency, budgets, timeout, supersession, and scheduling-result revalidation handled? |
| Revision and recovery | When can externally authored code replace a running behavior? What state, children, reservations, and evidence survive that transition or a process/world restart? |

Useful later discriminating cases are a crop completing while mining owns the player; a reflex interrupting a container transfer; two behaviors allocating the same wheat or fuel; a canceled parent with an outstanding LLM result; a lost event followed by state refresh; a site becoming ineligible for progress after departure; and a new behavior revision arriving while the old one has an active child. These are proposed review cases, not tests executed in this research.

## Limits and research-only resolution draft

This note compares documented contracts and selected repository source. It does not measure Minecraft cancellation latency, world ticking, navigation costs, or LLM performance. The consulted language/runtime examples are not implementation choices. No gameplay, build, runtime probe, or code change was performed; exact scheduler and human-in-the-loop decisions remain open.

Resolution draft: “Established four primary-source precedent families for the OS experiment: workflow activities/messages, structured concurrency, robotic action cancellation, and resource scheduling. The note distinguishes their guarantees from Airicraft's current FIFO watches and identifies the remaining ownership, handover, allocation, fairness, observation, judgment, and revision decisions. This resolves the fact-finding scope only; it selects no scheduler and implements no OS behavior.”
