# Sandbox runtimes for the Airicraft OS driver experiment

Date: 2026-09-15

Research ticket: [Establish viable sandbox runtimes for the driver experiment](https://github.com/shinohara-rin/airicraft/issues/54), part of [Chart the Airicraft OS driver experiment](https://github.com/shinohara-rin/airicraft/issues/51).

Scope: documentation and source research at repository base `9af5e6ec561d6652a2f788603276f05991c4d893`. No runtime, sandbox, performance, Minecraft, or recovery experiment was run. Upstream `latest` documentation and moving source branches were read on the date above; their capabilities must be tied to a selected release before implementation.

## Finding

There is a credible, bounded shortlist: **JavaScript/TypeScript in a custom QuickJS host; Luau in a custom host; GraalJS with its untrusted sandbox policy; or CPython/asyncio inside an OS-confined process**. All can represent several live behaviors waiting for host results. They differ substantially in what stops runaway computation, which authority the guest receives, and what must be packaged. The matrix and evidence below establish conditional feasibility, not a language selection or a security certification.

The experiment's fixed architecture is multiple code-defined, long-lived behaviors cooperating over one player. Airicraft OS executes and orchestrates them; external Codex authors and investigates their revisions. A callable LLM worker is an effect available to a behavior or scheduling policy, not an authoring agent implemented inside Airicraft. The mod retains Minecraft action control. This is consistent with the existing distinction between decision ownership, work outcomes, and the single foreground actuator in [ADR 0002](../adr/0002-system2-evidence-work-and-decisions.md); this note does not replace that ADR or settle the new scheduler contract.

## Options matrix

“Live suspension” means retaining a continuation in a running runtime. It does not mean restart durability. “Restricted host” means an embedding designed to expose only selected operations; a separate process alone does not establish filesystem or network confinement.

| Candidate | Live suspension and asynchronous calls | Compute and cancellation boundary | Isolation and authority | Research disposition |
| --- | --- | --- | --- | --- |
| **JS/TS → QuickJS, custom native host** | Promises, async functions, host-created promise resolvers, and a host-driven job queue. Several runtimes have separate heaps; contexts within one runtime can share objects. [Manual](https://bellard.org/quickjs/quickjs.html#Runtime-and-contexts), [C API](https://github.com/bellard/quickjs/blob/master/quickjs.h) | Runtime allocation/stack limits and an interrupt callback. Interruption raises an uncatchable exception; it is not a resumable timeslice. [Limits](https://bellard.org/quickjs/quickjs.html#Memory-handling), [implementation](https://raw.githubusercontent.com/bellard/quickjs/master/quickjs.c) | Custom API and module loader required; stock libc bindings expose files, subprocesses, and native modules. [Host library](https://raw.githubusercontent.com/bellard/quickjs/master/quickjs-libc.c) | **Rule in** as a deliberately small embedding. Host integration and diagnostics are owned by the experiment. |
| **Luau, custom native host** | Explicit coroutine yield/resume; the host resumes a waiting behavior with a result. Coroutine close is available for suspended/dead coroutines. A plain subprocess does not satisfy restricted-capability requirements. |

## What each candidate actually supplies

### QuickJS

The reviewed manual identifies QuickJS `2026-06-04`. Its allocation limit is per `JSRuntime`; several `JSContext`s within that runtime do not acquire separate allocation budgets. One runtime does not support simultaneous multithreaded execution. Therefore, one runtime per independently bounded behavior is a plausible arrangement, not a requirement or measured cost conclusion. [QuickJS manual](https://bellard.org/quickjs/quickjs.html#QuickJS-C-API)

`JS_NewPromiseCapability`, `JS_ExecutePendingJob`, the rejection tracker, memory accounting, and a configurable module loader provide the building blocks for an effect bridge. **Inference:** a host operation can enqueue bounded work and immediately return a promise; its completion can later be delivered on the runtime's owning execution path. The host must bound pending jobs and select when to execute them; draining one self-replenishing promise queue forever would defeat scheduling fairness. [QuickJS public header](https://github.com/bellard/quickjs/blob/master/quickjs.h)

Do not reuse the stock host unmodified. Its loader reads files and uses `dlopen`; other bindings implement process execution and URL fetching through a subprocess. An embedding can omit these bindings and replace loading with approved source modules. Its own C functions still execute with host authority. **Inference:** an engine interrupt callback does not establish a deadline for arbitrary blocking native code; effect handlers should return promptly, with separate supervision for work outside the VM. [QuickJS host implementation](https://raw.githubusercontent.com/bellard/quickjs/master/quickjs-libc.c)

QuickJS exposes exception retrieval and rejection tracking, but an Airicraft trace of pending effects and await reasons remains application data. Preserve source/debug information rather than stripping it. [QuickJS public header](https://github.com/bellard/quickjs/blob/master/quickjs.h)

### Luau

Luau removes `io`, `package`, filesystem-loading functions, and unsafe portions of `os`/`debug`; host-added APIs remain part of the boundary. Its sandbox guide specifically identifies `getfenv`/`setfenv` as isolation hazards and recommends separate VMs when stronger separation is needed. Its interrupt has eventual safepoint delivery, with an explicit caveat for long C calls. These are engine properties, not OS process containment. [Luau sandbox guide](https://luau.org/sandbox/)

Luau “threads” are coroutine execution states, not parallel OS threads. `lua_newstate` accepts a custom allocator; a quota implementation must account for Luau allocations and separately bound host buffers. The C API supplies stack inspection, breakpoints/stepping hooks, and interrupt callbacks. [Luau C API](https://luau.org/api/)

A behavior can yield an effect descriptor and resume with its result; the host must supply the dispatcher, timers, LLM calls, cancellation state, and result routing. This is a design inference from coroutine semantics, not a shipped asynchronous Minecraft API. Yielding is forbidden across some C/metamethod boundaries; adapters must use a supported yield/resume path. Closing a suspended coroutine destroys its stack and prevents further resume. [Luau coroutine library](https://luau.org/library/#coroutine-library)

### GraalJS

For untrusted source, `CONSTRAINED` and `ISOLATED` are not substitutes for `UNTRUSTED`. The policy restricts native access, process creation, host I/O and host-object exposure, and validates required configuration. Avoid broad Java objects: exported host methods still define the authority guests can exercise. [SandboxPolicy API](https://www.graalvm.org/sdk/javadoc/org/graalvm/polyglot/SandboxPolicy.html) Different trust domains require separate engines; contexts sharing an engine also share its sandbox policy. [Engine sharing](https://www.graalvm.org/latest/security-guide/sandboxing/)

The guide distinguishes hard isolate heap sizing (`engine.MaxIsolateMemory`) from soft retained guest heap measurement (`sandbox.MaxHeapMemory`). Host callback allocations are outside the latter; callback CPU time is included in `sandbox.MaxCPUTime`, while waiting on I/O typically is not. CPU enforcement can overshoot, and a statement counted by `sandbox.MaxStatements` is not constant-cost. Exceeding a resource limit cancels the context rather than yielding a continuation. [GraalVM resource limits](https://www.graalvm.org/latest/security-guide/sandboxing/#resource-limits)

Java can retain promise resolution callbacks and settle a guest promise later. However, the general interoperability examples are not proof that their host-access configuration works under `UNTRUSTED`: its scoped callback references and allowed host types must be respected. Inference: a restricted adapter may instead keep resolvers inside JS and deliver plain completion messages by request ID. [Promise interoperability](https://raw.githubusercontent.com/oracle/graaljs/master/docs/user/JavaInteroperability.md), [policy requirements](https://www.graalvm.org/sdk/javadoc/org/graalvm/polyglot/SandboxPolicy.html)

`Context.interrupt(Duration)` ends current execution while leaving the context reusable, runs guest `finally` blocks, and may time out on non-interruptible host code. `close(true)` cancels and closes the context. Neither is documented as saving the current continuation for later resume. [Context API](https://www.graalvm.org/sdk/javadoc/org/graalvm/polyglot/Context.html#interrupt(java.time.Duration)) Errors expose guest/host origin, source location, stack frames, interruption, and resource exhaustion. [PolyglotException API](https://www.graalvm.org/sdk/javadoc/org/graalvm/polyglot/PolyglotException.html)

**Availability is versioned:** the current guide explicitly advertises sandboxing on Oracle GraalVM and Community Edition from `25.1` with corresponding isolate artifacts; it also excludes the Node.js embedding and limits compatible language/options. This establishes documented availability, not that an arbitrary isolate artifact has been qualified here. [Compatibility](https://www.graalvm.org/latest/security-guide/sandboxing/#compatibility-and-limitations)

### CPython in an OS-confined process

`asyncio` suspends a task on a pending await and executes other tasks. CPU-bound code on that event-loop thread delays all of them. These tasks share their process, so killing that process loses every resident behavior; independently disposable behaviors need a smaller process grouping. Async I/O and subprocess integration are available, but adding threads or executors moves the work elsewhere rather than applying a budget to it. [Asyncio development guide](https://docs.python.org/3/library/asyncio-dev.html#concurrency-and-multithreading)

`Task.cancel()` requests an exception on a later event-loop cycle and the coroutine may suppress it. Task names, stack inspection, and exception inspection are useful diagnostics, not enforcement. [Task API](https://docs.python.org/3/library/asyncio-task.html#task-object) Python signal handlers can also wait arbitrarily long behind C calculations. [Signal semantics](https://docs.python.org/3/library/signal.html#execution-of-python-signal-handlers) An external supervisor can use process termination/kill, but cleanup handlers may not run, descendant processes are not automatically killed, and shared queues/locks can be left unusable. [Multiprocessing lifecycle](https://docs.python.org/3/library/multiprocessing.html#multiprocessing.Process.terminate)

`resource` offers process CPU, address-space and other limits subject to OS differences; its `prlimit` API is Linux-only. This research does **not** establish a portable hard RSS cap on macOS. A chosen confinement package must demonstrate the intended memory and process-tree limits. [Python resource API](https://docs.python.org/3/library/resource.html)

`-I` narrows import paths and ignores Python environment variables; it does not remove file, network, subprocess, or native-extension authority. Python explicitly rejects audit hooks as a sandbox and warns against subinterpreters for security-sensitive isolation. Thus restricting imports or using one interpreter per behavior does not complete this option. [Command-line contract](https://docs.python.org/3/using/cmdline.html#cmdoption-I), [audit warning](https://docs.python.org/3/library/sys.html#sys.addaudithook), [subinterpreter warning](https://docs.python.org/3/library/concurrent.interpreters.html#multiple-interpreters-and-isolation)

## Local macOS packaging and authoring

| Candidate | Documented feasibility and packaging consequence |
| --- | --- |
| QuickJS | Official Makefile supports macOS; engine is C with no external engine dependency. A native helper avoids requiring JNI in Minecraft, but its IPC/build/distribution would be new work. [Installation](https://bellard.org/quickjs/quickjs.html#Installation) |
| Luau | Official build supports CMake and macOS Makefiles. Embedding uses compiler and VM libraries; `luau-analyze` supplies type checking and linting. A custom helper still needs a release-pinned native build. [Upstream README](https://github.com/luau-lang/luau/blob/master/README.md) |
| GraalJS | Current embedding docs list JDK 21 host support through isolates, `darwin-aarch64` native artifacts, and an optional external subprocess isolate mode since GraalVM 25. Default isolates remain in-process. Default language artifacts use GFTC; community variants have distinct coordinates. [Embedding guide](https://www.graalvm.org/latest/reference-manual/embed-languages/) Current macOS distributions have removed x64 support. Intel support would need a separately justified supported version/path. [macOS support](https://www.graalvm.org/latest/getting-started/macos/) |
| CPython | Official macOS installers provide signed/notarized universal2 builds for Apple Silicon and Intel. That does not create an application-specific sandbox or dependency bundle. [macOS guide](https://docs.python.org/3/using/mac.html) `multiprocessing` defaults to `spawn` on macOS; its docs warn about fork safety and frozen-executable restrictions. A packaged supervisor must choose and qualify its own launch arrangement. [Process start methods](https://docs.python.org/3/library/multiprocessing.html#contexts-and-start-methods) |

For both JS engines, TypeScript adds author-facing types and transpilation; types are erased, so runtime inputs still require validation. Preserve the emitted code and source maps with each revision for diagnosis. Neither compatibility with Node packages nor a functioning TS debugger follows just from ECMAScript support. [TypeScript compilation](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types), [source maps](https://www.typescriptlang.org/tsconfig/sourceMap.html)

QuickJS and Luau both assume trusted compiler output when loading bytecode. Accepting arbitrary guest-supplied bytecode would bypass that assumption; source compilation and its resource budget belong to the hosting design. [QuickJS bytecode caveat](https://bellard.org/quickjs/quickjs.html#Script-evaluation), [Luau bytecode caveat](https://luau.org/sandbox/#library)

An OS confinement mechanism is a distinct packaging decision. Apple's supported App Sandbox workflow uses app capabilities and entitlements; an embedded command-line helper inherits its containing app's sandbox configuration. Therefore, merely launching a helper from Gradle/the wrapper establishes no such policy. A sandboxed helper packaging design must identify its actual filesystem/network permissions and allowed IPC, and verify them on the supported Macs. No App Sandbox configuration, signing workflow, container, VM, or Linux-specific restriction is selected or validated here. [Apple App Sandbox configuration](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox)

## Alternatives and shortcuts outside the shortlist

- **Starlark for bounded policy or explicit transitions:** the Go implementation has computation-step limits, cancellation, and stack diagnostics. Its grammar does not include `async`, `await`, or `yield`; these are reserved. It can host an explicit `state + event → next state + effects` model, or a blocking host builtin, but does not directly supply the desired asynchronous continuation authoring model. Rule it in only if the experiment chooses explicit transitions; do not invent a new resumable DSL during this research. [Language specification](https://raw.githubusercontent.com/google/starlark-go/master/doc/spec.md), [interpreter API](https://github.com/google/starlark-go/blob/master/starlark/eval.go)
- **Plain Node `vm` as a sandbox:** ruled out; its own documentation says it is not a security mechanism. This does not rule out Node inside a separately justified OS confinement design, which would be another packaging option rather than a free VM boundary. [Node VM documentation](https://nodejs.org/api/vm.html#vm-executing-javascript)
- **RestrictedPython as the isolation mechanism:** ruled out; its authors explicitly distinguish it from a sandbox or secured environment. It may restrict syntax but cannot substitute for the CPython option's external confinement. [RestrictedPython documentation](https://restrictedpython.readthedocs.io/en/latest/)

## Suspension, restart, and revision are separate contracts

The reviewed APIs establish **live** promise/coroutine/task retention. They do not establish a supported durable snapshot of arbitrary suspended stacks, pending host callbacks, and external operations. This is a limit of the evidence, not a claim that checkpointing is impossible.

In particular, QuickJS's version-bound bytecode and unstable binary-object format are not a durable workflow contract. [QuickJS persistence caveats](https://bellard.org/quickjs/quickjs.html#Script-evaluation) Python pickle saves top-level functions by qualified name, not their execution state, and can execute code during deserialization; it is not an untrusted continuation format. [Pickle contract](https://docs.python.org/3/library/pickle.html#what-can-be-pickled-and-unpickled) Luau's close operation discards the coroutine stack, and the Graal cancellation APIs unwind or close execution. [Luau coroutine close](https://luau.org/library/#coroutine-library), [Graal context lifecycle](https://www.graalvm.org/sdk/javadoc/org/graalvm/polyglot/Context.html)

There are at least three unresolved recovery choices: retain live instances only; restart from explicit versioned behavior state; or reconstruct state by replaying recorded inputs through a compatible program. None is selected. Replay would require control of clock/randomness, observations, effect results, scheduling order and code/runtime versions. For example, ECMAScript specifies implementation-dependent random-number generation and current-time reads, so a JS engine is not inherently a deterministic workflow runner. [ECMAScript random and date semantics](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-math.random)

**Design inference:** replay must consume recorded effects without issuing them again. A retry after “request accepted, result lost” needs reconciliation with the effect owner, not a guessed success/failure. A live frame also continues to reference its existing code: revision installation needs an explicit policy for keeping old instances, restarting, or migrating declared state. Retaining revision hashes, source maps, instance IDs, effect receipts and relevant observations gives external Codex evidence for a revision; it does not decide when to apply one.

## Worker and Minecraft effects need their own bounds

Language compute is only one resource consumer. The following are consequences of the fixed experiment boundary, not proposed scheduling policy:

- An LLM call may consume network time, tokens, provider budget, retry budget and host buffers while a behavior is suspended. These need independent admission, concurrency and completion rules. The guest should receive a callable operation/result contract; provider credentials and unrestricted HTTP do not need to be guest capabilities.
- Revoking or killing a behavior cannot by itself undo a Minecraft action or a provider request already accepted elsewhere. Cancellation needs distinguishable requested, acknowledged and terminal states, plus a rule for late results and lost connections. Existing executor-owned outcomes and foreground actuator ownership make that boundary explicit. [ADR 0002](../adr/0002-system2-evidence-work-and-decisions.md)
- Several suspended instances are not several simultaneous owners of one player's movement, inventory or GUI. Farm, mine and animal-care behaviors can wait independently while smelting proceeds as game-owned work; conflict arbitration and resource reservation remain OS/mod contracts. They are not supplied by promises, coroutine libraries or process isolation.
- Host decoding, logging, module compilation, queued completions and any native worker need bounded memory/work too. Guest limits do not cover all of them. Process supervision should remain able to diagnose/terminate a stuck runtime without requiring that runtime's event loop to cooperate.

A useful future reference trial would keep farming, mining, smelting and animal care instances alive, suspend at least one on an LLM worker, introduce a player-resource conflict and interruption, and retain evidence for an externally authored revision. Its purpose would be to distinguish continuation state, scheduling decisions, executor outcomes and revision identity. This research has not run or specified acceptance thresholds for that trial.

## Remaining decisions and qualification risks

1. **Trust and failure unit:** protect against accidental infinite loops only, or adversarial/dependency code too? Is a behavior, shared runtime, host process, or the entire driver allowed to fail together? This determines whether per-instance heaps/processes are necessary.
2. **Scheduling budget:** wall time, active CPU, interpreter steps, per-resume allowance, lifetime allowance, or a combination? Which overruns terminate a behavior and which merely stop scheduling it? How are runnable work and completion queues kept fair?
3. **Capability contract:** exact host operations, module allowlist, data schemas, credential ownership, payload limits and quotas. What crosses the runtime boundary by copy, and can any host object disclose additional authority?
4. **Cancellation/effect ownership:** what acknowledges release of the player, inventory reservation or workstation? How are late worker results, cancellation races, host death and orphaned work reconciled?
5. **Recovery/revision:** live-only or restartable instances; checkpoint/event retention bounds; replay determinism; behavior-version migration; treatment of in-flight effects. No recovery guarantee is implied by selecting a language.
6. **Packaging:** supported Mac architectures, pinned release and licenses, native/JVM dependency footprint, installed versus bundled runtime, and actual OS confinement policy. For Graal specifically, qualify `UNTRUSTED`, every required resource option, promise completion and diagnostics on the exact isolate artifact; the existence of an isolate is not sufficient evidence.
7. **Diagnostics and measurement:** runtime stacks plus authoritative instance/effect IDs, wait reasons, source revision, budget use, dropped-evidence markers and executor receipts. Measure runaway loops, allocation bursts, promise floods, blocking host calls, cancellation during I/O, host disconnects and late completions before claiming bounds. No latency, footprint, fairness, restart or adversarial-resistance measurements are available from this research.

This resolves the runtime fact-finding question while leaving language choice, hosting, resource/scheduling contracts, recovery guarantees and any human-in-the-loop decision open.
